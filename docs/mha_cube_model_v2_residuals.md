## 重复计时

完整调用做12轮，每轮每个候选预热30次，采61组覆盖全部split的样本，
组间轮换并反转候选顺序，轮间反转输入配置顺序。每个Event样本只调用
一次预构建callable，包含全部kernel及输出/临时分配对执行的影响；排除
编译、H2D、CPU参考与主机元数据准备，使用同一流和warm-cache。

组件阶段同样做12轮，每轮预热30次、61组样本。所有split>1的partial和
merge放在同一轮的样本组内交替测量，避免按split测完整个长会话后才换
下一个split。每个merge消费该split预先算好、保持存活的固定FP32局部结果；
partial调用的输出与这些固定merge输入分别分配。

组件计时与完整调用是独立会话，两者不能相加或相减当成精确开销分解。
split=1没有merge，直接使用完整调用作为参照。这里也没有采硬件流水计数器，
不能仅凭Event耗时断言具体指令或频率是根因。

## 摘要解释

- 各split完整调用耗时：12个轮中位数的中位数、最小/最大值及MAD。
- `faster_than_v2=X/12`：该split的轮中位数比V2选择更短的轮数。
- `vs_v2_range`：按轮计算的`V2耗时/该split耗时`范围，大于1表示该候选更快。
- partial/merge各自的轮中位数范围、MAD及比V2对应组件更快的轮数。
- 冻结V2对各split的预测值，便于对照模型排序与实测排序。
- JSON另存解析工作量：program数、按28核估算的波数、每请求KV块数、
  最长分片块数、空分片program数。这些是静态/元数据推算，不是profiler计数器。

如果原误选在绝大多数轮次仍出现，优先视为可重复的选择问题；再结合组件
的相对变化，判断额外开销主要出现在局部计算还是合并阶段。原始样本、p90
和每轮配对比值保留在报告/JSONL中，便于检查长尾。
这四种形状已经观察过，此次属于定向诊断，不称为新的独立验证集。
本地仅完成入口、统计与数据保存检查，实际重复计时待NPU执行。
